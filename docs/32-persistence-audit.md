# 32. Persistence audit: "real data entered by the user is saved"

Worker U3, 27 November 2026. Scope: `src/features/{journal,cbt,stories,community,doctors,crisis,consent,onboarding,assessment,chat,counsellor,followup,admin,modals}`, `src/shared/lib/storage`, `src/shared/lib/offline`, `src/shared/lib/api/{journal,safetyPlan,consents,account,chat}.ts`.

## Rule applied

Every input either:

1. is really stored and comes back after a reload and a new sign-in (Supabase table behind RLS, or the encrypted device store), with a success message shown only after the write was confirmed, or
2. says plainly that it is not saved.

When a save fails, the UI shows a `role="alert"` message and keeps what the user typed so they can retry. A list that fails to load shows an error with a retry button, never an empty state that looks like "you have nothing". Real accounts never see invented sample content. The offline preview ("Enter Demo") stays clearly labelled and session-scoped.

## Encrypted flows after a reload

Journal, thought records, CBT activity and worry tools, the safety card and session notes all need the vault passphrase again after a reload. The passphrase is held only in memory. The vault screen now says the data is still stored and nothing is lost. After unlocking, the data decrypts and shows (tested for each flow). A safety plan encrypted with its own passphrase shows its own lock panel, as described in #7.

## Honest limits (left as is)

* **Chat history is not stored.** The tables `chat_sessions` and `chat_messages` exist, but nothing writes to them: the edge function streams only, and `encrypted_content` needs a client key scheme. Wiring this up is a product and security decision (retention, encryption key, counsellor visibility), so the UI now says plainly that the conversation is not saved. **Lead:** decide whether to persist chat. If yes, it is an edge-function plus client-encryption task that needs no new table.
* **Story likes cannot be saved.** `posts.likes_count` exists, but there is no per-user likes table, and students may not update other people's posts under RLS. The like button was removed. **Lead:** if likes are wanted, a `post_likes(post_id, user_id)` table and RPC are needed. I did not create one.
* **CBT activities, worry time and safety-card anchors are stored on this device only.** They are encrypted, but they do not follow the student to a new device, and they are cleared on sign-out (`clearAllLocalUserData`). The UI says "Stored on this device only" and "Saved on this device." No backend table exists for them. **Lead:** a table is needed if they should sync.
* `mindsahaay_onboarding_completed` is a device-local flag and nothing reads it for routing, so a new device does not force onboarding again. The consents themselves are in the ledger.
* The offline preview ("Enter Demo") still uses clearly labelled preview data in Journal ("(Demo Data)") and in-tab state elsewhere. Its flag is session-scoped (another worker's change).
* `src/shared/lib/api/moods.test.ts` (outside my scope) fails one test, "enqueues mood entry when offline". It still sets the demo flag in `localStorage`, but the flag now lives in `sessionStorage`. **Fix:** change that line to `sessionStorage.setItem("mindsahaay_demo_mode", "true")`, as I did in the storage and outbox tests.
