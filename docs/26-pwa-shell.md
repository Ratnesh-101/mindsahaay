# 26. PWA shell and offline crisis access

Status: implemented and tested in desktop Chrome (Playwright, production build). Not tested on a real phone, Firefox or WebKit. The `pwa` Playwright project has 9 passing tests (2026-11-20). `UpdateToast` is mounted in `AppLayout` (`src/app/layouts/AppLayout.tsx`); it was built but not mounted when the independent review (docs/28, G6-SEC-04) looked at it.

## 1. How it works

- `public/manifest.webmanifest` makes the app installable: name and short name MindSahaay, `start_url` `/dashboard`, standalone display, theme colour `#19443c`, background `#fbf8f3` (the day-mode tokens from the design system). Icons: 192 and 512 px (`any`) and a 512 px maskable icon. The PNG files in `public/icons/` are generated by `node src/shared/lib/pwa/scripts/generateIcons.mjs` (Node built-ins only) and committed.
- `public/sw.js` is a hand-written service worker. It is a template: the Vite plugin `pwaServiceWorker` in `vite.config.ts` rewrites three marked constants and writes the final file to the build output.
  - `PRECACHE`: the app shell (`index.html`), `offline.html`, `offline.js`, the manifest, the icons, the entry chunk with its CSS and static imports, and the lazy chunks for `/login`, `/crisis`, `/chat` (with its two exercise modals) and `/dashboard` (the install start page). Names are read from `.vite/manifest.json` (`build.manifest = true`); no hashed name is written by hand.
  - `VERSION`: `computeCacheVersion(precacheList, helplinesSource)` from `src/shared/lib/pwa/cacheVersion.ts`. It hashes the sorted precache list plus the text of `src/shared/lib/pwa/helplines.ts`, so changing a helpline number, its wording or `HELPLINES_LAST_VERIFIED` changes the cache name `mindsahaay-shell-<version>`. Line endings are normalised so Windows and Linux builds agree. The hash is a non-cryptographic 53-bit hash (it only has to change, not resist attack).
  - `SHELL_ROUTES`: routes whose chunks are precached. Offline navigation to one of these gets the cached `index.html`.
- The plugin also renders the helpline list and verified date in `offline.html` from `helplines.ts`, so the offline page cannot drift from the app. The verified date appears in both language blocks and both are replaced.
- `offline.html` is bilingual (English and Hindi). Every text node exists in both languages with a `data-l="en"` or `data-l="hi"` attribute, and the helpline links exist once (only the Emergency label has two spans). `public/offline.js` (no inline script, because of the CSP) sets `html[lang]` to `hi` when `navigator.language` starts with `hi`, otherwise `en`, and updates the title and the list label. A visible link ("हिन्दी में देखें" / "View in English") switches language and remembers the choice in `sessionStorage` for the tab. Without JavaScript the page shows English. The Hindi text is not native-reviewed: see docs/27-hindi-review.md.
- `src/shared/lib/pwa/register.ts` registers the worker only when `import.meta.env.PROD` is true and the build is not a demo build (`VITE_DEMO_MODE=true`). The PWA end-to-end build sets `VITE_PWA_E2E=true` to opt in. `unregisterServiceWorker()` removes registrations and MindSahaay caches (test helper).

## 2. Cache strategy

| Request | Strategy | Cached? |
| --- | --- | --- |
| Navigation, online | Network | No |
| Navigation, offline, route in `SHELL_ROUTES` | Cached `index.html` | Precached |
| Navigation, offline, any other route | `offline.html` (three helplines, "Try again") | Precached |
| Static asset in the precache list | Stale-while-revalidate | Yes |
| Other same-origin GET not in the list | Not intercepted | No |
| Any cross-origin request (Supabase and others) | Not intercepted, network only | Never |
| Path containing `/functions/`, `/rest/`, `/auth/`, `/realtime/`, `/storage/` | Not intercepted | Never |
| Request with an `Authorization` header | Not intercepted | Never |
| Any non-GET | Not intercepted | Never |

Nothing that can carry personal data is stored. Only the static shell and build assets are cached. The e2e test lists every cache entry and fails if any URL matches a backend path or Supabase origin.

## 3. Update flow

1. The browser fetches `/sw.js` on navigation. A changed file installs a new worker beside the old one.
2. The new worker precaches its own cache and then waits. It does not call `skipWaiting` by itself, so nobody is reloaded in the middle of a breathing exercise.
3. `registerServiceWorker({ onUpdateAvailable })` calls the handler with an `apply()` function. `src/main.tsx` forwards it as a `mindsahaay:sw-update` window event (`detail.apply`). `UpdateToast` (`src/features/offline-ui/UpdateToast.tsx`, exported from the feature index and rendered once in `AppLayout`) listens for that event and shows a `role="status"` notice in English or Hindi with two buttons: "Refresh now" calls `detail.apply()` and shows "Updating…" while the new worker takes over, and "Later" hides the notice until the next update event. It is fixed at the bottom-left (SOS button is in the top bar, the offline banner is in the page flow), with 32 px targets. **To turn it on, add one line in `src/app/layouts/AppLayout.tsx`:** import `UpdateToast` from `../../features/offline-ui` next to `SyncChip` and render `<UpdateToast />` once inside the layout root. Until that line is added, the update applies after all tabs are closed.
4. `apply()` posts `{ type: "SKIP_WAITING" }`. The worker activates, deletes every `mindsahaay-shell-*` cache except its own, calls `clients.claim()`, and the page reloads once on `controllerchange`. The reload happens only after `apply()`, never on the first install.

## 4a. Crisis-consent cache freshness

The offline crisis path queues a crisis event from a consent flag cached on the device (`warmCrisisConsentCache` in `src/features/chat/api.ts`). That flag must follow the student's choice:

- `grantConsent` and `revokeConsent` in `src/shared/lib/api/consents.ts` (and so the `useGrantConsent` and `useRevokeConsent` hooks) call a helper after the ledger insert succeeds, only for the `crisis_intervention` purpose.
- The helper loads `features/chat/api` with a dynamic import (that module imports `consents.ts`, so a static import would be circular).
- On withdrawal it writes `false` to the cache first, before any network call. It then starts a refresh from the ledger. Since the review in docs/28 (G6-SEC-09) the cache is only a hint: offline events are queued whatever it says, and the outbox checks consent on the server before every send, dropping the event if withdrawn. So a withdrawal made on another device is honoured at send time even when the cache is stale.
- On grant it starts a refresh. The refresh does nothing while the browser is offline, and the cache is then corrected by the existing refresh on the `online` event in `AppLayout`.
- The helper catches every error. A cache problem never fails the consent change, and a failed insert never touches the cache.
- Limit: a student who grants consent while offline cannot happen (the insert needs the network). A consent changed on another device is picked up at the next sign-in or when the connection returns, not instantly.

## 5. Not covered

- The activation step that deletes older caches is not exercised end to end (it needs two builds in one run). It is a few lines in `sw.js`; verify by hand on release.
- iOS: install is manual (Share, Add to Home Screen), storage may be evicted after about seven days without use, and there is no install prompt. Not tested.
- Background Sync is not available on iOS Safari. Queued data must sync when the app is opened (see the outbox work).
- No real device install was tested (Android or iOS). Testing was desktop Chrome with `setOffline`.
- Client-side navigation to a route whose chunk is not precached, while offline, fails to load that chunk. Only a full navigation reaches the offline page.
- The Hindi on the offline page and in the update toast is machine-written and not reviewed by a native speaker (docs/27-hindi-review.md).
- Google Fonts are fetched from a third-party origin and are not cached. Offline text uses fallback fonts.
- Alerts remain in-app and are not monitored 24/7. Offline support does not change that.
- If the app is deployed under a sub-path, the plugin prefixes URLs with the Vite `base`, but the worker scope and the manifest paths assume `/`.
